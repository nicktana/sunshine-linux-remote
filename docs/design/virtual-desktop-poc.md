# Virtual desktop proof of concept {#virtual_desktop_poc}

This is the first virtual-mode milestone in the [Linux remote sessions design](linux-remote-sessions.md). Demonstrate one independent desktop under a dedicated unprivileged Linux account. Start it over SSH or a VM automation channel before anyone logs in on the physical seat. An unmodified Moonlight desktop client must be able to pair, open Desktop, see a Wayland application, and control it with a keyboard and mouse. Leave the display manager, physical session, and installed Sunshine instance outside the launch path. Automatic boot startup, a broker, multiple virtual sessions, and physical greeter streaming are later milestones.

## Stack selection

| Candidate | Capture, input, and startup implications |
| --- | --- |
| **Sway on wlroots** | Select the headless backend and Pixman software renderer. Sway exposes wlroots screencopy and the virtual keyboard and pointer managers. A private Wayland socket gives the capture process, input injector, and test applications a common desktop. Headless WayVNC uses the same family of protocols and provides an independent reference for the compositor setup. [Sway server](https://github.com/swaywm/sway/blob/master/sway/server.c) · [WayVNC headless FAQ](https://github.com/any1/wayvnc/blob/master/FAQ.md) |
| labwc on wlroots | A floating-window desktop and a plausible follow-up. Upstream documents screencopy and virtual input support, with protocol access policy to account for. Validate its active headless output and advertised globals before using it as a drop-in alternative. [labwc configuration](https://github.com/labwc/labwc/blob/master/docs/labwc-config.5.scd) · [labwc release notes](https://github.com/labwc/labwc/blob/master/NEWS.md) |
| Weston | Provides a headless backend and a PipeWire output backend. The latter supplies video without input. Weston's RDP backend has its own transport and does not supply a direct path through Sunshine's wlroots capture and input plan. Adopting Weston would require verifying a different capture and injection pair. [Weston backend documentation](https://wayland.pages.freedesktop.org/weston/toc/running-weston.html) |

Use **headless Sway, Pixman, wlroots screencopy into `wl_shm`, and Sunshine's software H.264 encoder**. Use compositor-scoped virtual keyboard and pointer injection. Start with one 1280×720 output at scale 1 and a 30 fps Moonlight stream. Pin and record the tested Sway/wlroots pair, distribution, and Moonlight version. Keep a native Wayland terminal or input observer as the test application. Disable XWayland, audio, controller support, native touch and pen, system tray, and UPnP for the fixture. KMS requires scanout, X11/NvFBC require an X display, and portal capture adds a session service and authorization flow that this stack can avoid.

## Session bootstrap and capture baseline

1. Use a disposable VM with a display manager and an existing dedicated account reachable by SSH or VM automation. Give the VM a reachable address on an isolated network and use Sunshine's standard ports there. This exercises normal Moonlight host add and pairing and avoids any dependency on custom port support or the installed host's listeners. Keep configuration, app list, pairing credentials, and logs in a private fixture directory.
2. Start Sway as the fixture account with a private, owner-only `XDG_RUNTIME_DIR`, mode `0700`, and a minimal config. Construct the child environment explicitly. Exclude the console's `DISPLAY`, `XAUTHORITY`, `WAYLAND_DISPLAY`, `WAYLAND_SOCKET`, `SWAYSOCK`, and session bus address. Set `WLR_BACKENDS=headless` and `WLR_RENDERER=pixman`. Start with a Wayland-native client that requires no D-Bus service. If a chosen application requires D-Bus, run the whole fixture under a private `dbus-run-session` and pass that bus address only to fixture children.
3. Discover the actual Wayland and Sway IPC sockets in that directory. Query active outputs with `swaymsg -t get_outputs` against the fixture IPC socket. Some versions can provision one output with `WLR_HEADLESS_OUTPUTS=1`. If none is active, use the pinned Sway version's `create_output` IPC command and configure the resulting output. Treat the name as discovered data. Sway can use `HEADLESS-1` for an internal fallback. Wait for one active output at the requested mode and for the registry to advertise `wl_shm`, the output and XDG output interfaces, `zwlr_screencopy_manager_v1`, `wl_seat`, `zwp_virtual_keyboard_manager_v1`, and `zwlr_virtual_pointer_manager_v1`. Use a bounded readiness check. [Sway command registration](https://github.com/swaywm/sway/blob/master/sway/commands.c) · [Sway output handling](https://github.com/swaywm/sway/blob/master/sway/commands/output.c) · [Sway IPC reference](https://github.com/swaywm/sway/blob/master/sway/sway-ipc.7.scd)
4. Start the terminal or observer inside the private compositor. Capture a known frame with a screencopy client such as `grim` and confirm keyboard and pointer delivery with a compositor-protocol client and a focused observer. Record formats, protocol versions and output identity. That isolates compositor problems before testing Sunshine.
5. Run the checkout's Sunshine binary in the foreground from a `cmake-build-*` directory, with the fixture's Wayland environment and explicit config. Set `capture = wlr`, `encoder = software`, `stream_audio = disabled`, and disable input for this first baseline. Select the discovered output using the identifier Sunshine logs. Restrict the app list to a command-free Desktop entry. Pair Moonlight using the ordinary Sunshine PIN flow and confirm a visible changing frame at 720p30. Use an isolated test network and require encrypted transport on the selected client where supported. Stop and reap the worker, app, and compositor on failure or fixture exit before discarding the runtime directory.

Open one dedicated input connection to the same explicit socket used by capture. Bind one seat and the virtual input managers on that connection. Serialize Wayland event dispatch and requests so input cannot race disconnect or object destruction. Install an XKB keymap before sending keys. Convert Sunshine's incoming normalized key codes to protocol keycodes using a verified mapping, including separate keypad and extended keys. Start with a fixed US layout and verify modifier state and key-up ordering. Map relative motion, output-relative absolute motion, mouse buttons and both scroll axes, then send pointer frame boundaries. Clamp absolute coordinates to the active output after applying Sunshine's viewport mapping. Keep a bounded pressed-key/button state and test disconnect, error and reconnect. Unicode text packets and extra devices are deferred. Sharing the Wayland socket means trusting applications running as the fixture account, so keep this account and its socket private to the test.

## Acceptance and sequencing

1. **Capture baseline.** Start before physical login, pair and stream the known fixture image with keyboard and mouse disabled. Confirm software encoding and SHM in logs and show that the physical session retains its own output. If capture fails, record the advertised globals and actual buffer offer before proposing a capture patch.
2. **Control baseline.** Enable the explicit Wayland input mode. Type letters and modifier combinations, move and click with relative and absolute input, and scroll on both axes. Verify that the observer receives the expected events and that a physical-session observer sees none. Repeat after logging in physically and focusing a different app. Check both that no device is created through uinput and that a physical pointer or keyboard cannot drive the virtual desktop.
3. **Recovery.** Disconnect with a held key and button, reconnect, and check for released state. Kill the compositor during a stream and check worker exit and fixture cleanup. Run negative cases with a missing or wrong socket, missing input globals, and denied virtual devices. A wrong target must be rejected by the fixture before Sunshine starts. A backend failure must never activate uinput.
4. **Regression coverage.** Add GoogleTest cases using `tests/tests_common.h` for backend selection and failure, keycode and button mapping, coordinate normalization, scrolling, modifier and held-state cleanup, and suppression of device creation. Cover default Linux input behavior through the existing tests. Confirm the Linux build with Wayland enabled and disabled. Run the end-to-end client checks manually or in a disposable VM and record versions and results.

A local smoke attempt found Sway 1.9. It required `--unsupported-gpu` on the development host because it detected proprietary NVIDIA drivers, then stopped before opening its Wayland socket. A separate Unix socket bind returned `EPERM` in the workspace sandbox. The recommended fixture is a disposable VM with software rendering and no NVIDIA passthrough. Sunshine capture, Moonlight pairing, and input delivery remain to be verified there.
